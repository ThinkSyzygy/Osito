# PROJECT-ORION — Desktop Environmental Sensor Enclosure

> **Fictional example:** every organization, person, email address, date, dimension, observation, and engineering conclusion in this directory is invented for Osito training.

PROJECT-ORION is a nonregulated desktop demonstration enclosure for a small indoor environmental-sensing circuit. It does not control equipment and must not be used for health, safety, regulatory, or emergency decisions.

This example shows how one small project moves from a charter through requirements, evidence, review, change control, lessons, and archive.

## Walkthrough

1. Start with [project metadata](project.yaml) and the [charter](project-charter.md).
2. Read the three [requirements](requirements/REQ-ORION-001.md), [service requirement](requirements/REQ-ORION-002.md), and [air-path requirement](requirements/REQ-ORION-003.md).
3. See how an uncertain placement condition remains an [assumption](assumptions/ASM-ORION-001.md).
4. Treat the [meeting note](meetings/MTG-ORION-001.md) as evidence, then inspect its separate [reviewed change set](meetings/CHG-ORION-20310410-001.md).
5. Follow the approved [enclosure decision](decisions/DEC-ORION-001.md) and linked [risk](risks/RSK-ORION-001.md).
6. Review the [research note](research/RES-ORION-001.md), [tolerance screen](calculations/CALC-ORION-001.md), and [validation record](validation/VAL-ORION-001.md).
7. Inspect the [design review](reviews/DR-ORION-001.md), resulting [change](changes/ECN-ORION-001.md), and [action](actions/ACT-ORION-001.md).
8. Finish with the [lesson](lessons/LSN-ORION-001.md) and [archive record](archive/README.md).
