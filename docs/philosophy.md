# Philosophy

Osito is built around a simple idea: useful engineering memory requires more than saving files. A team must know what is current, why it is believed, who accepted it, what remains uncertain, and how to recover the history.

## Evidence before polish

A concise dashboard is valuable, but it is not stronger evidence than the records that produced it. Current approved records should identify their sources. Generated summaries should remain reproducible and disposable.

## State and history serve different jobs

Current state should be easy to find and update. Historical evidence should remain intact. Mixing both into an endless chronological summary makes decisions harder to locate; deleting history makes them impossible to audit.

Osito therefore favors:

- current operational records updated through review;
- source notes and logs preserved as history;
- explicit closure and supersession;
- version control for prior file states.

## Uncertainty is information

An unknown input, unsupported claim, open assumption, or conflicting value should remain visible. Pressure to complete a document is not permission to invent an answer. Missing evidence is not a successful review result.

## AI proposes; people remain accountable

AI can classify notes, find related records, draft change sets, check structure, or explain a calculation. It should not approve its own proposal, accept technical risk, declare a phase passed, or turn a weak source into a confident fact.

Human review is especially important for:

- safety and regulatory matters;
- requirements and release criteria;
- calculations and technical conclusions;
- test interpretation;
- architecture and manufacturing commitments;
- privacy, licensing, and publication.

## Boundaries matter more than convenience

Searching every project can make an answer look complete while causing a confidentiality breach. Context should be gathered from the selected project and explicitly shared methods. Cross-project inclusion should be exceptional, reviewed, and recorded.

## Reversibility supports learning

Engineering work changes. A good operating system supports revisions without hiding them:

- stable IDs survive file renames;
- decisions can be superseded;
- risks can be closed with evidence;
- reviews can reject stale proposals;
- migrations can be previewed and rolled back;
- generated views can be rebuilt.

## Determinism and judgment have different roles

Automation is well suited to schema checks, link validation, arithmetic, hashing, duplicate detection, and reproducible selection. Humans remain responsible for meaning, adequacy, tradeoffs, and risk.

The framework keeps those roles visible instead of describing every automated result as intelligence or every judgment as deterministic.

## Practical completeness

Osito aims to be useful without requiring a consulting engagement or proprietary service. A small team should be able to understand, configure, operate, test, and extend it. Complexity should be added only when it protects an identified need.

## Honest claims

The repository is an alpha framework, not a finished platform. Passing checks does not guarantee privacy or design quality. A documented process does not establish compliance. An AI-assisted review does not replace a qualified reviewer.
